Usage log: how the whole platform is used

You asked for logs as files, kept locally, that can later be put together, analysed and one day sent to a server. That is built. Three choices remain that are yours, below. Each was built to the recommendation, so nothing waits on you.

Built

Four feeds, one log

Upstream Omnigent already records most of what we need. Its telemetry events and web analytics are switched off here because they would send data to the internet. We catch those events before they would leave and write them to a local file instead. We added two small feeds of our own: every pa command, and every tool or skill an agent uses.

Desktop packpa usage pack: one file to carry elsewhere

The log lives in the app folder (~/flight-deck/logs/ on the work Mac). Updates never touch it. Nothing changes on screen, so it never shows in a demo recording.

Built

What a line can hold

The rule is enforced in one place, the writer, so no caller can forget it. A line may hold numbers, yes or no, and short words with no spaces, such as ids, status words and file names. Anything with spaces, such as a prompt, a title or a document's text, keeps only its length.

The agent runs
pa init data/plan.json --title "Acquire Northwind before March"
The log keeps
pa.init  data=plan.json  title=<text 30>  exit=0

File and record names do get through, for example plan.json. That is the subject of question UL-2.

For testing

How it feeds the evals

The routing tests in the Aviator design (AV-6) grade what the agent did. Which skill did it load? Did it brief a thread? Did a turn fail? Today the only record of that is the transcript. With the log, the eval runner marks the start of each trial, and the grader reads that trial's lines directly.

pa usage eval start routing r-07 2     # every line now tagged routing / r-07 / trial 2
  … the trial runs …
pa usage eval stop
pa usage summary --suite routing       # trials stay out of your real numbers unless asked

One next step goes in with the routing suite. When Aviator offers a hero skill, the director skill would write pa log offer.made. That makes "did it offer?" something code can check, instead of a judge's call.

Question UL-1

Should usage logs go into the repo's git history?

You said "files in the repo". They are in the repo folder, but git ignores them. The question is whether any of them should be committed, which would make them travel with Send to repo the way the people and scenarios you publish do.

Recommended: logs stay out of git
flight-deck/
├─ workspace/      committed (D-75)

Alternative: the Mac mini commits packs

│  └─ mac-mini-2026-11-21.jsonl.gz
└─ logs/usage/     ignored

Every test day adds a file to git history,
which can never be fully removed.

Keep them out of git Recommended

Logs stay on each machine. To combine them, run pa usage pack and move the file. Git history stays clean, and nothing from the work Mac can be pushed by accident.

Mac mini packs go in with Send to repo

Test-day numbers travel with the code, so the production team sees real usage beside it. It is only safe because the Mac mini runs invented data. The work Mac has no git.

Commit the raw logs

Everything is versioned automatically. Every session adds noise to every pull request, and history grows by megabytes a week.

Question UL-2

What may a pack from the work Mac hold?

No sentences ever reach the log. Names do, though, and at work a file name can say something on its own. A fingerprint replaces each name with a short code that stays the same every time, so you can still count "the same dataset, edited 12 times" without knowing what it is called. Tools, skills, workflows, pages and status words always stay readable.

Names as written
pa.set  data=falcon-acquisition.json
        status=ready  workflow=intent-shaping
Fingerprinted
pa.set  data=#3f9a02c1d4
        status=ready  workflow=intent-shaping

Fingerprint work Mac packs Recommended

The work Mac's own log keeps names, so you can read it there. Any pack made there is run with --fingerprint. The Mac mini keeps names, since its data is invented.

Names as written everywhere

Everything is easiest to read. This relies on nobody giving a work file a revealing name.

Fingerprint everywhere

The safest choice, but even your own test logs on the Mac mini become harder to read.

Something else

For example, nothing leaves the work Mac at all for now.

Why the recommendation: it keeps the place where names matter (off the work Mac) safe, without making your day-to-day testing logs cryptic.

Decided while building (D-122 to D-127)

DDecision
D-122One local log: a JSON line per event, a file per day in logs/usage/. On by default, with an off switch. Updates skip it.
D-123Fed from upstream's own instrumentation and in upstream's field names, so the production team's pipeline can read it.
D-124The writer enforces "ids and words, never sentences". Packs are re-checked.
D-125Every pa command and every change in the Hangar logs itself. Reads are not logged. Skills use pa log only for moments pa cannot see.
D-126Eval trials are tagged and kept apart, and the routing graders read them.
D-127Until there is a server, a log leaves a machine only as a pack a person carries. Sending to a future server is a defined interface, and a person has to switch it on.
