Initiatives and templates

Initiatives and templates

The data model you asked for: an initiative registry with ids, artifacts that point back to it, a shared statement of intent, and one contract for templates whether they are markdown or JSON with views. Most of it is built (pull request 42). Two choices are yours, on the cards in the thread.

The short version

  • An initiative is a project with a goal. Its card gets a permanent id (ini_…) and key, so renaming it no longer breaks links.
  • Every artifact carries a small stamp saying which initiative, template, stages and sources it belongs to. The registry is read from those stamps, so there is nothing to keep in sync.
  • Each initiative has a shared intent document and four registers: evidence, open questions, decisions and ready checks. Every hero skill reads them and adds to them.
  • Templates come in three kinds with one manifest: markdown with sections, records with views, and self-contained pages.

The picture

Dashed lines are stamps: each artifact names its initiative. pa artifacts reads them all and groups them, so the registry is never stored and never out of date.

Templates: one manifest, three kinds

markdown

Sections and frontmatter

A template.md with headings and a list of sections, each owned by a stage. Intent briefs, PRDs, status updates.

records

JSON with views

Record schemas plus view-kit views for the canvas or chat. Catalogs, boards, the registers.

page

A self-contained page

One HTML file styled with tokens. Today's Library templates, unchanged.

{ "template": "initiative-intent", "version": 1, "kind": "markdown",
  "stage": "any", "out": "projects/{key}/intent.md", "file": "template.md",
  "sections": [ { "id": "problem", "heading": "Problem", "owner": "discover" },
                { "id": "scope",   "heading": "Scope",   "owner": "shape" }, … ] }

The registers, drawn

What every hero skill does

  1. Find the initiative from its brief or the list. Never create one; the lifecycle skill does.
  2. Read first: what exists, the intent document, open questions and past decisions.
  3. Stamp what it makes, starting documents from templates.
  4. Put checkable things in the registers, not buried in prose.
  5. Write only its own stage's sections of the intent document; suggest changes to the rest as tracked changes.
  6. Extend in its own space: new fields in its own records, new kinds as new templates.

The registers came from the lifecycle research thread: the gap none of the companies in your research has closed is research to intent with the evidence still attached.

Your two choices

Answer on the cards in the thread. What is built follows the recommendation, so either answer is a small change.

IN-1

Is an initiative the same thing as a project with a goal?

A
The same thingRecommended

One record. The project page, In flight and Connections all describe the initiative. Nothing new to learn.

B
A layer above projects

An initiative spans several projects (for example across teams). More flexible, but two near-identical words and a second page to keep.

C
The same as an area

The lasting problem space is the initiative, and goal projects sit inside it. Artifacts outlive any one release, but a release loses its own place for intent.

IN-3

What is the shared representation of the intent?

A
An intent document plus four registersRecommended

Judgment in prose, owned section by section; evidence, questions, decisions and ready checks as records any skill can check. Readable and checkable.

B
Structured fields only

Everything as JSON fields, documents rendered from them. Easy for agents, stiff for people, and loses nuance.

C
Just the card

The card points at the latest brief. Lightest, but nothing shared holds open questions or decisions across skills.
