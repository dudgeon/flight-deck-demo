Workflow Prototyping System
Product Aviator · system design · draft 1 · 20 Nov 2026

A system for inventing workflow types

We do not yet know how product work should be staged, paced or reviewed. The demos exist to find out. So the system is designed around one rule: every product question is answered by editing a scenario, and none is answered by changing the app.

The app knows five general things. Scenarios, carried by skills, know everything specific. A new use case costs a folder of files.

Part 2

The five things the app knows

Each is general on purpose. None mentions requirements, dependencies or PRDs.

ViewSomething drawn in a frame. Either free HTML from any skill, or a short spec that configures a standard layout. The same view runs in the chat, in the canvas, and alone in a browser.Two lanes, one frame
DatasetA named set of linked records in the project folder. Views are bound to it and redraw when it changes. Skills change it through one data command, which writes a local file now and can call a remote service later.The single source of truth
ActionA named event from a view, with the record it concerns: start, approve, return, edit. Simple edits change the dataset directly. The rest go to the session and show in chat as a small chip.How a button reaches the agent
Work productAnything worth coming back to: a document, a view of a dataset, a summary. The rail lists them, and any session in the project can open them.What the rail's Outputs shows
FlowAn optional, ordered list of stages. Each stage names a skill, its views and its work products. The order is advice. People can move both ways, and stages never lock anything.A lens over the data
Part 3

State belongs to records, not to the process

This is what keeps the system from fitting one use case too closely. Whether items move together or separately, and whether early ideas lock while others are revisited, is not something the app decides.

Every record carries its own state

  • Status: queued, working, needs you, ready for review, reviewed, returned, failed. A scenario may add its own.
  • Stage: where this record is in the flow, if there is one.
  • Locked: the person has settled this and it should not change without them.
  • Stale: something this record was built from has changed, so it deserves another look.

What that buys

  • All together, each at its own pace, or a mix: all are just patterns in the data.
  • Iterative intent works. Revising a requirement marks what was derived from it as stale, instead of throwing it away or silently keeping it.
  • Parts that are locked early keep moving while the rest is still being argued.
  • The board, the rail and a chat card all read the same fields, so they never disagree.
Part 4

The frame a view must respect

The view builder skill is taught these limits, and the preview harness enforces them, so a view is tested in both places before it reaches a demo.

In the chat narrow, brief

  • One column, roughly 480 to 720 wide.
  • Height is capped. Longer content offers Open in canvas.
  • One main action. No scrolling inside scrolling.
  • Once answered it freezes and stays as a record.
  • The agent may be waiting on it, or it may only be showing something.

In the canvas wide, lasting

  • Any width from about 480 to full screen; it must reflow.
  • Two levels: the collection and one item. The kit decides how an item opens.
  • Stays open for hours. Redraws when the dataset changes, without losing your place.
  • Sits in a tab beside documents and other views.
  • The agent can read it and operate it, and you watch that happen.

In both places: self-contained and offline, light and dark, colors and type only from the shared tokens, statuses only from the shared vocabulary. Free HTML is exempt from the tokens but not from the sandbox.

Part 5

What a scenario is made of

A scenario is a skill folder in a standard shape. The app reads the manifest and nothing else needs to be registered.

The folder

skills/prd-to-requirements/
  SKILL.md          how the agent runs it
  flow.json         stages, launchers, work products
  schemas/          the shape of each record type
  views/            specs, or free HTML
  fixtures/         invented data for demos
  script.json       optional scripted demo steps

A view spec

{ "layout": "tree-table",
  "data": "requirements",
  "group": "capability",
  "columns": ["title", "priority", "status"],
  "edit": ["priority", "locked"],
  "actions": ["start-explore"],
  "detail": "views/requirement-detail.json" }

Short enough for a small model to write correctly, and for you to change by hand between two demo runs.

Part 6

The tooling, and the loop it serves

Two authoring skills and one harness. The goal is that a new use-case idea becomes a clickable demo in one sitting.

View builder skill

Makes or changes one view. It knows the frame limits, the tokens and the standard layouts. It renders the result with fixture data at chat and canvas sizes, in light and dark, and looks at it before saying it is done. When a spec cannot express an idea, it writes free HTML and notes what the kit is missing.

Scenario builder skill

Given a use case in a sentence or two, it writes the whole folder: record schemas, a realistic fixture, the stage list, view specs and the skill that runs it. It asks you about the product, not about the plumbing.

Preview harness

One standalone page that draws the workspace (chat, canvas, rail) and plays a scenario from its fixtures and script, with no agent running. It is where views are tested, and it doubles as a demo you can show anywhere.

Checks

A script that confirms a scenario is self-contained, its fixtures match its schemas, every action a view sends is one the skill handles, and nothing reaches the internet.

Views in the chat is the largest and the least certain piece. It touches how upstream draws the transcript, which is where staying compatible matters most. It needs a closer look at the code before I would commit to an approach.
