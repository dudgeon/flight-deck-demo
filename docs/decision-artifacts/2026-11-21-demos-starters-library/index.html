Demos, starters and the Library

You asked how demo sessions, the scenarios built in the Hangar, and the Library you see while flying relate. Today they don't, cleanly. This page shows why, proposes one model, and asks three questions. The questions are also on cards in the thread.

The short answer

A scenario is a demo. It is a story with invented documents, invented data, a cast, and what each cast member knows. You build it in the Hangar. Once published, it shows up in the Library while flying with two buttons:

  • Play runs the click-through. It is scripted, needs no agent, and gives the same result every time.
  • Run live starts a demo session. That is a real session with Aviator, in a project of its own, already loaded with the story's documents and data. Its cast know their part of the story.

A starter (today's "canned session") is different. It starts real work on your material, using the same kind of work, with nothing invented. The Library holds both, in separate sections, so nobody mistakes the Allowances story for their own work.

2 · The proposed model

Three things, each with one job

Workflow
A kind of work: steps, record shapes, views, instructions. Built in the Hangar. A flier never picks one directly; they meet it through a starter or a demo.
Starter
A way to start a workflow on your own material. It asks for blanks, then opens a normal session in your project. Nothing invented. This is today's canned session under the name the Hangar already uses.
Demo
A story that runs one or more workflows: invented documents and data, a cast, what each cast member knows, a screenplay, and the opening line. Built in the Hangar (today's "scenario"). It can be played (click-through) or run live (a demo session).

The rule underneath: invented material only ever reaches a session through a demo, and a demo never writes into your own project. That one rule removes the leak in the first diagram.

Question 2 · D-61
What should "Run live" do with the story's documents and data?

A · Open a demo project Recommended

A new project per demo, loaded with the story. The cast get the story's facts.

  • Your real work never sees invented files
  • Reset is easy: rebuild the project
  • Uses per-project context, which already exists (D-15)
  • One more project in the sidebar per demo you've run

B · Load it into your current project

Copy the story's files into the project you're in, as happens by accident today.

  • No new projects
  • Invented PRDs and data sit beside your own
  • Hard to undo after a run

C · No live runs

Demos are click-through only. Live work only ever starts from a starter.

  • Least to build
  • No way to show the real agent on a known story
  • Cast never learn their part

A says what it's for in the words you already used ("demo sessions"), and one word in both modes avoids the confusion that started this thread. B keeps the term used in D-42 and the docs. With any choice, folder and file names can stay scenarios/, the way the repository kept omnigent-slim under the Flight Deck name (D-35).

6 · What this means for the scenario builder (slice 3)

Small additions to the D-42 folder

The Hangar builder thread is already moving each demo into its own folder. This proposal adds three things to that folder and one rule. They don't need your decision. They follow from the answers above.

# workspace/scenarios/<id>/ (shown as a Demo) scenario.json workflow(s) it runs, title, summary, cast, opening line ← new: goes into the composer on Run live context/ invented documents ← new: moved out of workspace/context/ fixtures/ invented datasets cast/<person>.md what each cast member knows in this story ← new script.md the screenplay for Play

The rule: a workflow's SKILL.md never copies demo files on its own. If you give it nothing, it asks. Today three skills copy the Allowances files in quietly, and that's how invented material ends up in real work.
