A map of the work a product agent has to hold

A product manager moves between loose thinking and structured work many times in one sitting. This page names eight ways of working, shows where each one lives in the workspace, and sorts every piece of interface into what Omnigent already gives us and what we have to make.

The chat coachesConversation, questions, and small interactive widgets that appear in the flow.
The canvas holds structureDocuments, catalogs, boards and reviews the PM can touch and the agent can see and change.
The rail keeps your placeProgress, outputs, context and what is waiting on you.
Skills bring the templatesA skill that knows this surface can build the interface the work needs.

      Part 4

      Two kinds of template, one contract

      Chat widgets and canvas templates differ in size and lifespan, but a skill should drive both the same way: name a template, hand it data, and get structured answers back. The proposal is one primitive, a view, made of a template, a dataset and a list of actions. The same view file runs in three places: inline in the chat, in the canvas, and standalone in a browser as a demo. The app then needs only three general mechanisms (a frame in the chat, a dataset the view is bound to, and a channel for actions) instead of one native component per idea.

      Chat widget

      Small, appears in the conversation, usually answered once. The multiple-choice question is the simplest member of this family.

      Lives
      In the transcript, at the point it was asked.
      Made of
      The same kit as the canvas, at chat size: choice, form, table, chart, status list, review card. Whether these are HTML views or native parts is the first open question.
      Answers
      The agent waits. The answer comes back as data, and the widget stays as a read-only record.
      Good for
      Scoping a job, confirming a finding, a quick look at numbers.
      widget_ask({
  template: "scope-form",
  data: { title: "Catalog setup", fields: [...] }
})  →  { sections: ["4", "5"], depth: "atomic" }

      Canvas template

      Large, stays open, edited by the PM and the agent over hours or weeks. It shows a dataset; it does not own it.

      Lives
      In the canvas, backed by a data file in the project folder.
      Made of
      A shared kit: tree table, status pill, board, drill-in panel, review bar.
      Answers
      Direct edits save to the data file. Requests that need the agent go to the chat as a message you can see.
      Good for
      A requirements catalog, a dependency board, a decision table.
      canvas_open({
  template: "work-board",
  data: "data/dependency-map.json"
})  // agents write the file, the canvas refreshes

      One status vocabulary for every work item

      Twenty workflows are only manageable if each one is always in exactly one of these states, on the board, in the rail and in chat.

      QueuedNot started yet.
      WorkingAn agent is on it.
      Needs youBlocked on a question for the PM.
      Ready for reviewFinished, not yet looked at.
      ReviewedThe PM signed it off.
      ReturnedSent back with a note.
      FailedStopped with an error; can be retried.
      Part 5

      Tooling for the prototyping sprint

      You will be building many scenarios quickly. These make a new flow cheap to write and hard to get wrong.

      Component kit

      One inlined stylesheet and script that every template shares, so a skill writes data, not layout. Works offline.

      Template gallery

      A Library view that shows each widget and canvas template rendered with fixture data, so you can browse and copy.

      Fixture packs

      Invented but realistic datasets (a PRD, 20 requirements, a platform map) so a flow can be demoed with no real documents.

      Flow manifest

      A short file in each skill that lists its templates, its launchers and its data shapes. The Library and the rail read it.

      Template check

      A script that confirms a template is self-contained, matches its data shape, and renders in light and dark.
